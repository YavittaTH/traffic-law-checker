## E1 — Retrieval: ภาษาพูด vs ภาษากฎหมาย

**ปัญหา:** ผู้ใช้พิมพ์ "มอไซค์ ไม่ใส่หมวกกันน็อค ฝ่าไฟแดง" แต่ตัวบทเขียน "รถจักรยานยนต์ ... หมวกที่จัดทำขึ้นโดยเฉพาะเพื่อป้องกันอันตราย ... สัญญาณจราจรไฟสีแดง"

**ชุดทดสอบ:** `eval/dev_retrieval.jsonl` (18 เรื่อง, 22 ข้อหาที่คาดหวัง)

> ⚠️ **ชุด dev นี้ไม่ใช่ผลวัดจริง** ผู้พัฒนาเขียนทั้งคำถามและตารางแปลงคำ (`legal_terms.py`) เอง และปรับตารางจนชุดนี้ผ่าน ตัวเลขจึงสูงเกินจริงแน่นอน ใช้ดูทิศทางเท่านั้น ผลที่รายงานต้องมาจาก gold set ที่เขียนแยก (`eval/scenarios.jsonl`, `eval/heldout.jsonl`)

**คำสั่ง:** `python eval/run_retrieval.py`

### ระดับมาตรา (มาตราที่กำหนดหน้าที่ของข้อหาที่คาดหวัง)

| mode | recall@1 | recall@3 | recall@5 | all-found@5 | MRR |
|---|---|---|---|---|---|
| BM25 ดิบ | 36.1% | 38.0% | 43.5% | 38.9% | 0.425 |
| BM25 + ตารางแปลงคำ | 58.3% | 81.5% | 83.3% | 83.3% | 0.720 |

### ระดับข้อหา (บัญชีข้อหา: คำอธิบาย + ข้อความในระเบียบข้อ 11 + อนุมาตรา)

| mode | recall@1 | recall@3 | recall@5 | all-found@5 | MRR |
|---|---|---|---|---|---|
| BM25 ดิบ | 54.6% | 73.1% | 77.8% | 77.8% | 0.701 |
| BM25 + ตารางแปลงคำ | 93.5% | 100% | 100% | 100% | 1.000 |

**สิ่งที่เรียนรู้**

1. **ตารางแปลงคำ** (regex 27 แถว แต่ละแถวต่อท้ายถ้อยคำในตัวบท) ช่วยทั้งสองระดับ (มาตรา 43.5% → 83.3%)
2. **ค้นจากมาตราอย่างเดียวมีเพดาน** เพราะบางข้อหาอ้างมาตราที่เขียนกว้าง: ไม่หยุดให้คนข้ามทางม้าลาย = มาตรา 21 "ต้องปฏิบัติตามสัญญาณจราจรและเครื่องหมายจราจร" ซึ่งไม่มีคำว่าทางข้าม ส่วนย้อนศร = มาตรา 33 "ขับรถในทางเดินรถด้านซ้าย" → จึงเพิ่ม**บัญชีข้อหา** ซึ่งได้คำอธิบายภาษาที่ใกล้ภาษาคนจากระเบียบข้อ 11
3. ข้อที่พลาดก่อนปรับ (บันทึกไว้เป็น error analysis): "ขับรถเร็ว" ไม่ตรงกับ pattern "ขับเร็ว" และ "ขับ 140 ป้ายบอก 90" ไม่มีคำว่า "เร็ว" เลย → เพิ่ม pattern ตัวเลขความเร็ว
4. ข้อความจากราชกิจจาฯ บางคำสระสลับ (เช่น "ทศิ ทาง" ในมาตรา 41) ทำให้ token ไม่ตรง ส่วนนี้ dense retrieval น่าจะช่วยได้

### ผลบนชุดหลักแบบยาก (`eval/scenarios.jsonl`, ตารางล็อกแล้ว)

ชุดหลัก 31 ข้อ (20 ข้อที่ผิด ใช้วัด retrieval) เขียน**หลังล็อกตาราง** และจงใจให้ยาก: ภาษาพูดไม่มีคำหลัก, สะกดผิด, แสลง, ตัวเลขเป็นคำ, คำปฏิเสธ, หลายข้อหา, ไม่ผิด, นอกขอบเขต ผู้เขียนยังเป็นผู้พัฒนา (Claude) จึงต้องระบุในรายงาน แต่ไม่ได้แก้ตารางหลังเห็นผล · **เจ้าของโปรเจกต์ตรวจคำตอบครบ 41 ข้อแล้ว ถูกทุกข้อ**

| ระดับ | mode | recall@1 | recall@5 | all-found@5 | MRR |
|---|---|---|---|---|---|
| มาตรา | BM25 ดิบ | 17.5% | 27.5% | 25.0% | 0.253 |
| มาตรา | BM25 + ตาราง | 35.0% | 52.5% | 45.0% | 0.525 |
| ข้อหา | BM25 ดิบ | 30.0% | 51.7% | 45.0% | 0.496 |
| ข้อหา | BM25 + ตาราง | 44.2% | **75.0%** | 70.0% | 0.700 |

**เทียบกับชุด dev (100%)** → ช่วงห่าง 25 จุดคือขนาดของ bias จากการเขียนข้อสอบเองแล้วปรับตาม

**ข้อที่พลาด (ระดับข้อหา) เป็นภาษาพูดไม่มีคำหลักทั้งหมด:** s01 "ปาร์ตี้ หมดไปหลายขวด" (เมา), s03 "เหลือง แล้วก็แดง แต่ผมเร่ง" (ฝ่าไฟแดง), s05 "ขี่ขึ้นไปบนทางที่คนเดิน" (ทางเท้า), s06 "เกือบร้อยหกสิบ เขาให้ร้อยยี่สิบ" (ขับเร็ว), s13 "ขับกลับไวๆ ประมาณ 140" (ขับเร็ว), s15 "เป่าแล้วเกิน" (เมา) → ตารางแปลงคำเพิ่มได้ไม่รู้จบ จึงต้องให้ **LLM เขียนคำค้นใหม่ (query rewrite) ในขั้น agent** ซึ่งเป็นการทดลองถัดไป (ห้ามแก้ตารางเพื่อให้ข้อเหล่านี้ผ่าน)

held-out 10 ข้อ (`eval/heldout.jsonl`) **ยังไม่ได้รัน** จะรันครั้งเดียวตอนท้าย

### Dense / Hybrid (multilingual-e5-small, รันบนโน้ตบุ๊ก CPU)

| ระดับ | mode | recall@1 | recall@3 | recall@5 | all-found@5 | MRR |
|---|---|---|---|---|---|---|
| มาตรา | BM25 + ตาราง | 58.3% | 81.5% | **83.3%** | 83.3% | **0.720** |
| มาตรา | dense | 16.7% | 33.3% | 57.4% | 55.6% | 0.324 |
| มาตรา | hybrid (RRF) | 44.4% | 65.7% | 74.1% | 72.2% | 0.590 |
| ข้อหา | BM25 + ตาราง | 93.5% | 100% | **100%** | 100% | **1.000** |
| ข้อหา | dense | 57.4% | 63.0% | 73.1% | 66.7% | 0.690 |
| ข้อหา | hybrid (RRF) | 71.3% | 95.4% | 100% | 100% | 0.861 |

**ข้อสังเกต**

1. **dense (e5-small) อ่อนกว่า BM25 + ตารางมาก** และการรวมแบบ RRF ทำให้อันดับแย่ลง (MRR มาตรา 0.720 → 0.590) RRF ให้น้ำหนักสองรายการเท่ากัน รายการที่แย่จึงดึงรายการที่ดีลง
2. **ปัญหา hub:** มาตรา 11 (เปิดไฟเวลาแสงไม่พอ) และ 20 (รถบรรทุกต้องมีสิ่งป้องกันของตกหล่น) ติด top-5 ของ dense/hybrid เกือบทุกคำถาม ทั้งสองมาตราสั้นและใช้คำทั่วไปเรื่องคน รถ และทาง ("มองเห็นคน รถหรือสิ่งกีดขวางในทาง", "ผู้ขับขี่ซึ่งขับรถบรรทุกคน สัตว์ หรือสิ่งของ") ทำให้ vector ใกล้กับคำถามแทบทุกเรื่อง
3. **dense ช่วยได้บางข้อ** ที่ BM25 ดิบพลาด เช่น d01 มือถือ และ d13 ง่วง (dense พบมาตรา 43) แต่ตารางแปลงคำแก้ข้อเหล่านี้ได้อยู่แล้ว
4. **การเปรียบเทียบนี้เอียงเข้าข้าง BM25:** ตารางแปลงคำถูกปรับบนชุด dev เดียวกันนี้ ส่วน dense ไม่ได้ปรับเลย ข้อสรุปจริงต้องมาจาก gold set ที่เขียนแยก

**การตัดสินใจ (ชั่วคราว):** ใช้ **BM25 + ตารางแปลงคำเป็นค่าเริ่มต้น** ส่วน dense/hybrid เก็บไว้เป็นทางเลือกเพื่อทดสอบบน gold set

**สิ่งที่ควรลองต่อ** (เลือกจากผล gold set ไม่ใช่ชุด dev)
- โมเดลที่ใหญ่กว่า: `BAAI/bge-m3` (`python scripts/build_index.py --model BAAI/bge-m3 --out data/index_bge`)
- ส่งคำถามที่ขยายด้วยตารางแปลงคำให้ dense ด้วย (ตอนนี้ dense ใช้คำถามดิบ)
- RRF แบบถ่วงน้ำหนัก (เช่น BM25 1.0 / dense 0.5) หรือใช้ dense แค่เติมผลเมื่อ BM25 หาไม่เจอ


## E2 — Agent vs LLM-only baseline (ชุดหลัก 31 ข้อ, gemma-4-E4B-it)

ผลเก็บใน `eval/results_agent_e2/` (ตารางแปลงคำยังล็อกอยู่: unchanged)

- **baseline:** LLM เรียกครั้งเดียว มีรายชื่อ 23 ข้อหาใน prompt ไม่มีตัวบท ไม่มี tool ไม่มี grounding
- **agent:** LLM เขียนคำค้นภาษากฎหมาย → ค้นบัญชีข้อหา/ตัวบท → JSON → grounding → ค่าปรับคำนวณด้วยโค้ด

| baseline | 87.1% | 92.3% | 80.0% | 85.7% | 77.4% (24/31) | 61%–90% |

| tag | n | agent | baseline |
|---|---|---|---|

พฤติกรรม agent: เรียก LLM เฉลี่ย 3.0 ครั้ง/เรื่อง, 3.2 วินาที, search_offenses 45 ครั้ง, compute_penalty 4 ครั้ง, **grounding แก้คำตอบ 0 ครั้ง** (ไม่มีข้อหาที่แต่งขึ้น)

**วิเคราะห์ความผิดพลาด**

1. **agent ดีกว่าที่เรื่องผิดหลายข้อ** (recall ข้อหา 90% เทียบ 80%): baseline ตกข้อหาที่สอง เช่น s16 ได้ "ประมาท" แทน "หลับใน" และ s20 ตก "มือถือ" ส่วน agent ค้นทีละการกระทำ
2. **ทั้งสองระบบระวังเกินไปในเรื่องที่ไม่มีคำหลัก** (s01 ดื่มหลายขวดแล้วขับ, s03 ไฟแดงแล้วเร่งผ่าน, s09 ไม่ได้รัดอะไร): ตอบ need_more_info เหมือนกันทั้งคู่ → ปัญหาอยู่ที่การตีความของ LLM ไม่ใช่ retrieval (retrieval ระดับข้อหาได้ recall@5 75% บนชุดนี้)
3. **agent ลากข้อหาเกินเหตุ:** s31 ไม่เปิดไฟหน้า → abnormal_driving (43(5) "ไม่อาจแลเห็นทางด้านหน้า") ซึ่งพอมีเหตุผลแต่เกินไป และ s08 เฉี่ยวแล้วหนี → เพิ่ม reckless ข้อสันนิษฐาน: เมื่อ agent เห็นผลค้นที่ "ใกล้เคียง" จึงอยากใช้
4. **ความต่างโดยรวมแค่ 2 เรื่อง** ช่วงความเชื่อมั่นทับกันมาก จึงยังสรุปไม่ได้ว่าต่างอย่างมีนัยสำคัญ

## E3 — ปรับ prompt หนึ่งรอบ (ทั้ง agent และ baseline)

**สิ่งที่เปลี่ยน:** เพิ่มหลักการทั่วไปสองข้อใน prompt ของ**ทั้งสองระบบ** (เพื่อให้ยังเทียบกันได้อย่างยุติธรรม)
1. ตีความภาษาพูดแบบที่คนทั่วไปเข้าใจ ใช้ need_more_info เฉพาะเมื่อไม่รู้ว่าการกระทำนั้นเกิดขึ้นหรือไม่ ไม่ใช่เพราะเรื่องเล่าไม่ได้ใช้คำทางการ
2. เลือกข้อหาเฉพาะเมื่อถ้อยคำในตัวบทตรงกับการกระทำจริง ถ้าต้องตีความให้กว้างเกินไปจึงจะเข้า ให้ตอบ out_of_scope และอย่าเพิ่มข้อหาที่เรื่องไม่ได้เล่า

**กันการ overfit:** ไม่ใส่ตัวอย่างที่ตรงหรือคล้ายข้อในชุดหลัก, ไม่แก้ retrieval (ไฟล์ที่ล็อกยังเหมือนเดิม), ปรับรอบเดียวแล้วรันชุดหลักซ้ำ จากนั้นรัน held-out ครั้งเดียว

ผลเก็บใน `eval/results_agent_e3/` (retrieval ยังล็อก: unchanged)

| system | status acc | offense P | offense R | offense F1 | exact match | exact 95% CI |
|---|---|---|---|---|---|---|
| agent E2 → **E3** | 87.1% → **90.3%** | 93.1% → 93.5% | 90.0% → **96.7%** | 91.5% → **95.1%** | 83.9% → **87.1%** (27/31) | 74%–97% |
| baseline E2 → E3 | 87.1% → 87.1% | 92.3% → 92.6% | 80.0% → 83.3% | 85.7% → 87.7% | 77.4% → 77.4% (24/31) | 61%–90% |

| tag | n | agent E2 → E3 | baseline E2 → E3 |
|---|---|---|---|
| no_keyword | 8 | 50% → **88%** | 50% → 62% |
| single | 11 | 64% → 91% | 64% → 73% |
| multi | 9 | 100% → 89% | 67% → 67% |
| need_info | 3 | 100% → **67%** | 100% → 67% |
| out_of_scope | 4 | 75% → 75% | 100% → 100% |

**รายข้อที่เปลี่ยน (agent):** ดีขึ้น s01 (ดื่มหลายขวด → drunk), s03 (ไฟแดงแล้วเร่ง → red_light), s08 (เลิกเพิ่ม reckless) · แย่ลง s16 (เพิ่ม no_regard_safety เกินมา), s27 (ชนท้ายเบา ๆ → out_of_scope แทน need_more_info) · ยังผิดเหมือนเดิม s09 (ไม่ได้รัดอะไร → need_more_info), s31 (ไม่เปิดไฟหน้า → abnormal_driving)

**ข้อสรุป**
1. หลักการ "ภาษาพูดไม่ใช่ข้อมูลไม่พอ" ได้ผลชัดกับ agent (no_keyword 50% → 88%) แต่มี**ราคา**: ระบบถามกลับน้อยลง จึงพลาดข้อที่ควรถามจริง (need_info 100% → 67% ทั้งสองระบบ)
2. หลักการ "ห้ามลากข้อหา" ได้ผลไม่สม่ำเสมอ: แก้ s08 ได้ แต่ s16 กลับเพิ่มข้อหาเกิน และ s31 ไม่เปลี่ยน
3. agent ได้ประโยชน์จาก prompt เดียวกันมากกว่า baseline (+3 ข้อ เทียบ +0) ช่องว่างจึงกว้างขึ้นเป็น 3 ข้อ แต่ช่วงความเชื่อมั่นยังทับกัน
4. **ตัดสินใจ: หยุดปรับที่ E3** (ดีกว่า E2 ทุกตัวชี้วัดหลัก) แล้วรัน held-out ครั้งเดียว


## E4 — held-out (รันครั้งเดียว ด้วยระบบ E3)

`python eval/run_agent.py --gold eval/heldout.jsonl --out eval/results_agent_heldout --final` — รันแล้ว 1 ครั้ง (31 ต.ค. 17:18) ผลใน `eval/results_agent_heldout/`

| system | status acc | offense P | offense R | offense F1 | exact match | exact 95% CI |
|---|---|---|---|---|---|---|
| agent | 90.0% | 88.9% | 80.0% | 84.2% | 80.0% (8/10) | 50%–100% |
| baseline | 90.0% | 88.9% | 80.0% | 84.2% | 80.0% (8/10) | 50%–100% |

**เสมอกัน 8/10** แต่ผิดคนละข้อ:
- **agent ชนะ h06** (เด็กไม่มีคาร์ซีท + ไม่หลบรถฉุกเฉิน): baseline เดา no_regard_safety แทน emergency_no_yield → agent ยังทำเรื่องผิดหลายข้อได้ดีกว่า (multi 3/3 เทียบ 2/3) สอดคล้องกับชุดหลัก
- **agent แพ้ h03** (เข้าซอยป้ายห้ามเข้า สวนทาง → ควรเป็น wrong_way): agent ตอบ **no_plate** ข้อสันนิษฐาน: คำว่า "ป้าย" ในคำค้นไปตรงกับ "แผ่นป้ายทะเบียน" ในบัญชีข้อหา ผลค้นจึงชี้ผิดทาง แล้ว LLM เชื่อผลค้น → **ตัวอย่างที่ retrieval ทำให้แย่ลง** ส่วน baseline ที่เห็นรายการเต็มตอบถูก
- **ผิดทั้งคู่ h01** ("ตั้งวงกับเพื่อน ... ขับเองเพราะคิดว่ายังไหว" ควรเป็น drunk): agent ตอบ need_more_info, baseline ตอบ no_violation → การตีความภาษาพูดที่ไม่มีคำหลักเลยยังเป็นจุดอ่อน แม้ปรับ prompt ใน E3 แล้ว

**ข้อสรุปจาก held-out**
1. ชุดหลักหลังปรับ (87.1%) ใกล้กับ held-out (80.0%) **ไม่มีสัญญาณ overfit รุนแรง** แต่ held-out มีแค่ 10 ข้อ (1 ข้อ = 10%, CI 50–100%) จึงยืนยันอะไรได้น้อย
2. ภาพรวมทั้งสองชุด (41 ข้อ): agent 35/41 (85.4%) · baseline 32/41 (78.0%) → agent ดีกว่าเล็กน้อย จุดแข็งชัดคือเรื่องผิดหลายข้อ จุดอ่อนคือผลค้นที่ผิดชี้นำ LLM ได้
3. grounding ไม่ต้องแก้คำตอบเลยทั้งสองชุด

## E5 — RAG แบบ demo ของวิชา: เลือก k และ min_score (ชุดหลัก, ไม่ใช้ LLM)
